              ↓

              ↓
        대화/실행 모두 JSONL로 영속 저장 (분석·DB 친화)

이메일 / 보고서 / 요약 / 데이터 분석 / 비교 분석 5가지 업무 템플릿이
구조화된 폼으로 실행됩니다.

1. RAG 기본 개념 (5분 복습)
────────────────────────────────────────────────────────────────

RAG (Retrieval-Augmented Generation):
  LLM이 답을 만들기 전에, 외부 지식 (사용자 문서·웹 등)에서
  관련 조각을 "검색"해 와서 컨텍스트로 함께 넣어주는 패턴.

왜 필요한가:
  1) LLM은 학습 시점까지의 지식만 알고 있음 → 최신 정보 못 다룸.
  2) 내 회사·연구실 문서는 학습에 안 들어가 있음.
  3) 환각 (hallucination) 줄이려면 답변을 "근거"에 묶어야 함.
  4) 출처를 명시하면 신뢰도 ↑, 검증 가능.

기본 흐름:
  1. 문서를 작은 조각 (chunk) 으로 자름.
  2. 각 청크를 벡터로 변환 (embedding).
  3. 사용자 질문도 벡터로 변환.
  4. 벡터 공간에서 가까운 청크를 top-K개 검색.
  5. 그 청크들을 LLM 프롬프트에 컨텍스트로 같이 넣음.
  6. LLM이 그 컨텍스트만 가지고 답하도록 시킴.

[시나리오 A] PDF 업로드부터 첫 답변까지

  1. 사용자: 문서 탭 → Q1_report.pdf 업로드
  2. parse_file(): Docling으로 마크다운 + 페이지 메타 추출
  3. chunk_elements(): 문단 단위로 묶어 500자 청크 + 페이지 번호 보존
  4. embedder.encode(): BGE-M3 또는 MiniLM으로 벡터화 (CPU/GPU 자동)
  5. render_pdf_pages_to_dir(): 각 페이지 PNG로 렌더 (멀티모달 대비)
  6. save_doc(): meta.json + embeddings.npy + pages/ 디스크 저장
  7. 사용자: 채팅 탭 → "Q1 매출 성장률은?"
  8. rewrite_with_context(): 이전 대화 없음 → 원문 그대로
  9. expand_queries(): HyDE/multi-query 비활성 → variants = [원문]
  10. dense_search() + bm25_search(): 각각 top_n=20
  11. rrf_fuse(): RRF로 결합 → top_n 후보
  12. rerank(): cross-encoder로 재정렬 → top_k=5
  13. per_doc_min check: 1개 문서뿐이라 균형 보장 skip
  14. build_messages(): 시스템 프롬프트 + Context + 질문
  15. stream_chat(): 토큰 단위로 placeholder에 누적 표시
  16. split_thinking(): <think>...</think> 인라인 제거 (있을 경우)
  17. parse_citations(): 답변 안의 [1], [2] 추출
  18. render_assistant(): 답변 + 청크 popover + 추론 expander
  19. save_current_session(): .data/sessions/{id}.json
  20. auto_title_session(): 첫 턴이면 LLM이 8자 제목 생성
  21. log_turn_structured(): logs/{id}.jsonl 한 줄 추가

────────────────────────────────────────────────────────────────
6. 핵심 설계 결정과 트레이드오프
────────────────────────────────────────────────────────────────

(1) 청킹: paragraph + size cap + sliding window 폴백
  장점: 의미 단위 보존하면서 길이도 제한
  단점: 표/코드블록 같은 구조 무시 (Docling 사용 시 일부 보존됨)
  대안: semantic chunking (LLM으로 의미 경계 찾기) — 비싸지만 정확

(2) 검색: Dense + BM25 + RRF (하이브리드)
  Dense (BGE-M3)만 쓰면: 의미는 잡지만 정확한 키워드 (이름/숫자) 놓침
  BM25만 쓰면: 키워드는 정확하지만 동의어/패러프레이즈 못 잡음
  RRF: 두 랭킹의 역수 합 → 양쪽 모두에서 잘 잡힌 청크가 상위
  설정: 고급 검색 설정에서 모드 변경 가능 (hybrid/dense/bm25)

(3) 재정렬: cross-encoder
  retrieval 1차는 빠른 벡터 검색 → 후보 top_n (예: 20)
  재정렬은 cross-encoder가 (질문, 청크) 쌍 점수 산출 → top_k (예: 5)
  품질↑ 속도↓ trade-off
  무료 티어 RAM 부족 시 OFF 권장

(4) HyDE / Multi-query / Contextual rewrite
  - Multi-query: 같은 질문을 N개 표현으로 paraphrase → recall ↑
  - HyDE: LLM이 가상 답안 작성 → 그걸 임베딩 → 실제 답안과 의미 비슷한 청크 끌어옴
  - Contextual rewrite: 이전 대화 보고 대명사·생략 자동 보완
    (예: "그건 어떻게 되는데?" → "X 정책의 적용 절차는?")
  모두 LLM 호출 추가됨 → 속도/비용 trade-off

(5) 문서별 균형 보장 (per-doc reservation)
  현실 문제: top_k=5인데 1번 문서가 점수 강해서 5개 모두 점령
  해결: 각 문서에서 최소 1개 (또는 N개) 청크를 강제로 reserve
  비교 질문 ("vs", "차이", "비교") 감지 시 자동으로 2로 상향

(6) 영속 저장: 임베더별 격리
  같은 문서를 BGE-M3로 임베딩한 것과 MiniLM으로 한 것은 다른 벡터
  → .data/BAAI_bge-m3/ vs .data/sentence-transformers_paraphrase.../
  임베더 모델 바꿔도 이전 캐시 안 깨지고 보존

(7) 로깅: JSONL 한 줄 = 한 턴
  Postgres 친화 스키마: turn 단위 행 + retrieved/settings JSONB
  pandas로 즉시 로드: pd.read_json('logs/*.jsonl', lines=True)
  분석 예: "재정렬 켰을 때 인용률 차이는?", "모델별 평균 응답 시간?"

  │ Qwen3-Thinking, DeepSeek-R1     │ content 안 <think>..</think>│
  │ openai/gpt-oss-*, Kimi-K2*      │ reasoning_content 필드      │
  │ OpenAI o1/o3/o4                  │ 숨김 (reasoning_tokens만)   │
  │ DeepSeek-V4-Pro, Gemma-4 일반   │ 추론 없음 (직접 content)     │
  └────────────────────────────────┴────────────────────────────┘

  대응:
    1. delta.reasoning_content / delta.reasoning 캡처 (스트리밍 시)
    2. 끝난 뒤 content 안의 <think>..</think> 추가 split (split_thinking)
    3. 그 외 (<|channel>thought\n..<channel|> Gemma 4 포맷) 도 같이 처리

────────────────────────────────────────────────────────────────
10. 자주 발생하는 오류 카탈로그 + 해결
────────────────────────────────────────────────────────────────

[A] LLM API 관련

  A-1. "Unsupported parameter: max_tokens" (OpenAI gpt-5 / o-series)
       원인: GPT-5 시리즈와 o1/o3/o4 reasoning 모델은 max_completion_tokens 사용
       해결: _build_completion_params가 자동 분기. 직접 수정 불필요.

  A-2. "Unsupported value: temperature does not support 0.7" (OpenAI gpt-5)
       원인: GPT-5는 temperature=1.0만 허용
       해결: 자동으로 GPT-5/o-series에는 sampling 파라미터 미전송.

  A-3. "Unrecognized request argument supplied: top_k" (OpenAI)
       원인: OpenAI는 top_k 모름
       해결: _is_openai_endpoint() 감지 후 extra_body에서 제거.

  A-4. "top_k: property 'top_k' is unsupported" (HF Router Cerebras)
       원인: Llama-3.1-8B / gpt-oss 등 Cerebras 서빙 모델
       해결: HF Router는 기본적으로 top_k 미전송 (provider별 다름).

  A-5. "Model not supported by any provider you have enabled" (HF Router 400)
       원인: 해당 모델이 어떤 inference provider에도 deploy 안 됨
       해결: 다른 모델 선택, 또는 모델 카드의 "Inference Providers" 박스 확인

  A-6. "Authentication failed" / 401 (LLM API)
       원인: API 키 미설정·만료·권한 부족
       해결: .env 또는 Streamlit secrets 확인. 새 키 발급.

  A-7. "Could not finish the message because max_tokens was reached" (o3-mini)
       원인: reasoning 모델이 토큰을 추론에 다 써버림
       해결: max_tokens (= max_completion_tokens)를 1500+ 로 자동 상향됨

[B] 검색·임베딩 관련

  B-1. CUDA OOM / 메모리 부족 (BGE-M3 + Reranker)
       원인: 두 모델 합쳐 ~3GB, 무료 Streamlit Cloud의 RAM 초과
       해결: 설정 → 임베딩 모델을 MiniLM으로, 재정렬 OFF.

  B-2. 첫 임베딩 매우 느림
       원인: 첫 사용 시 모델 가중치 다운로드 (BGE-M3 ~2.2GB, Reranker ~580MB)
       해결: 정상. 다음 실행부터는 디스크 캐시에서 즉시 로드.

  B-3. PDF에서 텍스트 추출 안 됨
       원인: 스캔 이미지 PDF, 또는 PDF 내부 텍스트가 제대로 인코딩 안 됨
       해결: OCR이 필요 (Docling이 RapidOCR 사용 시도). 그래도 실패하면
             해당 PDF는 인덱스에서 제외 (st.warning 표시됨).

  B-4. 답변이 "제공된 자료에서는 답을 찾을 수 없습니다"만 나옴
       원인 후보:
         (a) retrieval이 관련 청크를 못 잡음 (top_k 너무 작음, 임베더 약함)
         (b) LLM이 시스템 프롬프트 너무 엄격 해석
         (c) 질문이 너무 모호 (HyDE / Multi-query 켜보기)
       해결: 검색 미리보기로 어떤 청크가 잡히는지 먼저 확인.
             top_k 늘려보기, 임베더를 BGE-M3로, HyDE 켜기.

  B-5. 청크가 한 문서에 다 쏠림
       원인: 한 문서의 임베딩 점수가 다른 문서보다 일관되게 높음
       해결: 설정 → "여러 문서 균형 검색" ON, per_doc_reserve 2+ 로.
             또는 채팅 상단 "문서 N/M ▾" 에서 직접 선택.

[C] 웹 검색 관련

  C-1. "No module named 'tavily'"
       원인: Tavily provider 선택했지만 tavily-python 미설치
       해결: pip install tavily-python (또는 DuckDuckGo로 변경)

  C-2. DuckDuckGo 검색 실패 / 빈 결과
       원인: rate limit, network, 또는 ddgs 라이브러리 버전 이슈
       해결: 몇 초 후 재시도, 또는 Tavily 키 발급해서 그쪽 사용

  C-3. "Tavily API 키가 비어 있습니다"
       원인: TAVILY_API_KEY 환경변수/secrets 미설정
       해결: .env 또는 Streamlit secrets에 추가, 또는 provider를 duckduckgo로

[D] Streamlit 배포 관련

  D-1. Streamlit Cloud "Unexpected error" on deploy
       원인 후보:
         (a) 조직 repo + OAuth 승인 없음 → clone 실패
         (b) slug 중복
         (c) 무료 티어 private 앱 슬롯 초과
       해결: slug 다른 걸로 / 조직 OAuth 승인 / public 전환

  D-2. "Repository not found" on git push
       원인: 토큰 권한 부족 또는 잘못된 repo URL
       해결: PAT에 repo scope 있는지, URL의 owner/name 정확한지 확인

  D-3. Streamlit Cloud 빌드 timeout
       원인: requirements.txt에 무거운 의존성 너무 많음 (docling 등)
       해결: 무거운 건 requirements-extras.txt로 옮김 (이미 분리됨).

  D-4. 재배포 후 .data, logs 사라짐
       원인: Streamlit Cloud 파일시스템은 ephemeral
       해결: 영속 필요하면 Postgres/S3 연결. 데모용으론 사용자에게 안내.

[E] Streamlit 런타임 관련

  E-1. "set_page_config can only be called once" 또는 비슷한 메시지
       원인: st 함수 호출이 module load 중 중복
       해결: app.py 상단의 set_page_config가 단 한 번만 호출되는지 확인.

  E-2. 사이드바 버튼 누른 후 변화 없음
       원인: rerun이 안 일어남, 또는 다른 변수가 같이 변함
       해결: 버튼 핸들러 안에서 st.rerun() 명시적으로 호출됐는지 확인.
             버튼 key 충돌 없는지 확인 (모든 key 고유해야).

  E-3. 추론 모델 응답에 <think>...</think>가 그대로 노출됨
       원인: split_thinking 패턴 불일치 (모델별 thinking 포맷 다름)
       해결: 모델이 어떤 포맷으로 thinking을 내는지 보고 패턴 추가.
             현재 지원: <think>, <|channel>thought\n..<channel|>

[F] 기타

  F-1. 로고가 화면에 안 보임
       원인: logo/real_logo.png 경로 잘못, 또는 파일 누락
       해결: ls chatbot_demo/logo/ 로 파일 존재 확인. 코드의 LOGO_PATH가
             올바른지 확인. 없으면 코드의 fallback (텍스트만)으로 동작.

  F-2. JSONL 파일이 너무 큼
       원인: text 필드를 자르지 않으면 한 턴이 수십 KB 가능
       해결: log_turn_structured가 chunk text를 1200자로 cap. retrieved 청크 텍스트도 동일.

  F-3. 채팅 입력창이 화면 가려져 안 보임
       원인: CSS의 stHeader 숨김 + padding 조합 문제
       해결: app.py 상단의 CSS 블록 검토 (padding-top, max-width 조정).

────────────────────────────────────────────────────────────────
12. 챗봇 서비스로 만들기 — Streamlit 기반 가이드
────────────────────────────────────────────────────────────────

이 장은 "내 노트북에서 잘 도는 챗봇"을 "다른 사람도 매일 쓰는
서비스"로 옮길 때 알아야 할 핵심을 정리합니다. Streamlit + 외부
LLM API 조합 (본 프로젝트와 유사한 구성) 기준이고, 코드보다는
의사결정과 함정 위주로 봅니다.


A. "서비스" 라고 하려면 더 챙겨야 하는 4가지
────────────────────────────────────────────

  데모는 "내가 시연 가능" 까지, 서비스는 "내가 자고 있어도 동작"
  이라야 합니다. 그 차이는 결국 다음 4축에 모입니다.

    1) 사용자가 두 명 이상  → 격리와 인증이 필요
    2) 컨테이너가 재시작     → 외부 영속 저장소가 필요
    3) 외부 API 가 가끔 죽음  → 친절한 에러와 fallback 필요
    4) 누가 무엇을 했나 모름  → 로깅과 분석이 필요

  본 강의 12장은 이 4축을 차례로 짚어갑니다. Streamlit 자체는 위
  4가지를 "기본으로" 해주지 않습니다 — 우리가 추가해줘야 합니다.


B. 사용자가 두 명이 되는 순간 — 격리와 인증
────────────────────────────────────────────

  데모일 때는 한 사람만 쓰니까 신경 안 써도 됩니다. 그런데 친구에게
  링크 보내는 순간 다음 의문이 따라옵니다.

    Q1. 내가 올린 PDF 를 다른 사람도 볼까?
    Q2. 내 대화 기록을 다른 사람이 이어받을 수 있나?
    Q3. 누가 들어와서 쓰고 있는지 알 수 있나?

  결론: Streamlit 의 session_state 는 "이 브라우저 탭" 단위로
  분리되어 있어서 메모리는 일단 격리됩니다. 그런데 디스크에 쓰는
  순간 (.data/, logs/) 사용자 구분이 사라집니다.

  ★ 핵심 원칙: 디스크에 쓰는 모든 경로에 user_id 를 끼워 넣는다.

    .data/{user_id}/...
    logs/{user_id}/...

  user_id 를 어떻게 정할지가 다음 결정. 옵션:

  ┌─────────────────┬─────────────────────────┬────────────────────┐
  │ 방식            │ 적합한 경우             │ 단점               │
  ├─────────────────┼─────────────────────────┼────────────────────┤
  │ 익명 UUID       │ 가입 없이 즉시 사용     │ 다른 기기/탭이면   │
  │ (브라우저별)    │ 데모, 사내 광범위 배포  │ 별도 사용자로 인식 │
  │                 │                         │                    │
  │ 비밀번호        │ 사내 소수 인원, 친구    │ 가입/회전 수동,    │
  │ (st.secrets)    │ 그룹                    │ 평문 보관         │
  │                 │                         │                    │
  │ OAuth (Google,  │ 진짜 서비스, 외부 공개  │ 자가호스팅 또는    │
  │ GitHub, SSO)    │                         │ 별도 인증 컴포넌트 │
  └─────────────────┴─────────────────────────┴────────────────────┘

  본 프로젝트는 위 두 가지 (익명 + 비밀번호) 를 자동 선택합니다.
  secrets.toml 에 [users] 블록이 있으면 로그인 강제, 없으면 익명.
  서비스로 진짜 키울 거면 세 번째 (OAuth) 로 가야 합니다.

  ★ 한 가지 절대 잊지 말 것:
    사용자가 user_id 를 직접 정할 수 있게 하면 "../admin" 같은
    값으로 파일 경로를 깨뜨릴 수 있습니다 (path traversal).
    영숫자+점/언더스코어/하이픈 만 통과시키는 정규화 함수를 한 번
    거쳐서 디스크에 쓰는 게 안전.


C. 데이터를 잃지 않으려면 — Cloud 의 가장 큰 함정
──────────────────────────────────────────────────

  ★ 반드시 알아야 할 사실:

    "Streamlit Community Cloud 의 파일시스템은 휘발성 (ephemeral)
     이다."

  즉 코드 한 줄 고쳐서 push 하거나, Reboot 한 번 하거나, 며칠 트래픽
  없어서 idle 되면 → /mount/src/<app>/ 안의 모든 파일 (업로드된
  PDF, 대화 기록 jsonl, 임베딩 인덱스) 통째로 사라집니다.

  "사용자가 어제 올린 파일이 오늘 안 보이는데요?" → 99% 이 함정.

  해결 갈래 (난이도 순):

  1) 처음부터 외부 DB 에 적재
     사용자 활동을 로컬 파일에만 두지 말고 Supabase / Neon Postgres /
     Firebase 같은 외부 DB 에 동시에 기록.
     본 프로젝트의 Supabase 연동이 이 패턴.

  2) 외부 객체 저장소
     큰 파일 (사용자가 올린 PDF, 이미지) 은 DB 대신 S3 / R2 / GCS 에.

  3) 자가호스팅
     VPS 또는 사내 서버에 Docker 로 띄우면 파일시스템이 진짜 영속.
     Streamlit Cloud 의 무료성을 포기하는 대신 통제권 얻음.

  추천 시작점: **"무엇이 사라지면 사용자가 화나는가" 부터 물어보기.**
  대화 기록은 화남, 임베딩 인덱스는 다시 만들면 되니 덜 화남, 모델
  가중치 캐시는 신경 안 씀. 우선순위 매겨서 영속화.

  ★ Supabase 가 일반적인 선택이 되는 이유:
    - 무료 티어 500 MB (소규모 서비스 충분)
    - Postgres 라 표준 SQL 로 분석/이관 자유
    - REST API 클라이언트가 깔끔 (한 줄 INSERT)
    - 보안 정책 (RLS) 기본 제공

  연동 자체는 5분 셋업이지만 처음 가는 사람은 다음 3가지에서 막힙니다.
  외운다 생각하고 봐주세요:

    (가) Project URL 은 "발급" 받는 게 아니라 프로젝트 만들면 자동.
        형식: https://<프로젝트-ref>.supabase.co
        대시보드 주소의 /project/<여기>/ 가 그 ref.

    (나) anon public 키는 코드에 박지 말고 secrets 에. service_role
        키는 절대 클라이언트에 두지 말 것 (관리자 권한 풀).

    (다) 새 테이블 만들면 RLS (Row-Level Security) 가 켜져 있을 수
        있고, 켜져 있으면 anon 키로는 INSERT 가 거부됩니다. 막히면
        제일 먼저 의심.


D. LLM 어디서 부를까 — 공급자 선택과 의존성 관리
─────────────────────────────────────────────────

  챗봇은 LLM API 에 의존합니다 → 그 API 가 죽으면 우리 서비스도 죽음.
  처음부터 다중 공급자 지원으로 짜는 게 큰 보험.

  네 갈래의 선택:

    OpenAI 직접 호출
      장점: 가장 안정, 도구 (function calling) 강력
      단점: 가격, 한국어가 최강은 아님

    Hugging Face Inference Router (본 프로젝트 기본)
      장점: 한 토큰으로 수십 가지 오픈모델 (Llama, Qwen, Gemma, ...)
      단점: provider 별 quirk (특정 파라미터 거부 등)

    DashScope (Qwen 공식)
      장점: 한국어/중국어 강한 Qwen3 직빵
      단점: 결제 등록 필요, 해외 사용자 latency

    자가호스팅 (vLLM, llama.cpp)
      장점: 토큰 단위 비용 없음, 데이터 외부 유출 없음
      단점: GPU 가 필요, 운영 부담

  ★ 코드 작성할 때의 1원칙:
    **"OpenAI 호환 API"** 만 받아들이는 단일 클라이언트로 통일.

  HF Router, DashScope, vLLM 모두 OpenAI-호환 endpoint 를 제공합니다.
  base_url 만 바꾸면 같은 코드로 호출 가능 → 사용자가 UI 에서 골라
  쓰게 됨.

  ★ 주의해야 할 것: 공급자 마다 받아들이는 파라미터가 미묘하게 다름.
    OpenAI gpt-5/o-series 는 max_tokens 대신 max_completion_tokens
    어떤 공급자는 top_k 를 거부
    어떤 공급자는 reasoning 토글이 다른 위치

  처음엔 이걸 모르고 짜다가 "왜 GPT-5 만 안 되지" 같은 함정에 빠집니다.
  공급자 분기 로직 (model 이름 → 파라미터 변환) 을 따로 함수 하나로
  두는 게 정신건강에 좋습니다.

  ★ 비용 인지: 종량제 API 는 사용자가 길게 쓸수록 비용 증가.
    응답에 포함되는 usage.prompt_tokens / completion_tokens 를
    누적해 로그에 남기면 월말에 "누가 얼마 썼나" 가 한눈에.


E. 무엇을 기록하고 어떻게 들여다볼까 — 로깅
──────────────────────────────────────────

  로깅은 "에러 났을 때 보는 것" 만이 아닙니다. 서비스 운영의 눈입니다.

  매 활동을 한 줄씩 구조화 (JSON) 로 남기면 한 달 후 다음 질문에
  답할 수 있게 됩니다.

    - 지난주 활성 사용자 수?
    - 가장 많이 묻는 질문 카테고리?
    - 어느 모델이 가장 자주 실패?
    - RAG 가 인용을 잘 만드나? (질문 대비 인용 수)
    - 응답 평균 latency? 그 분포의 꼬리는?
    - 사용자가 첫 대화에서 떠나나, 두 번째도 오나?

  ★ 무엇을 기록할지 — 3 가지로 충분:

    1) 대화 턴 — 사용자 메시지 + 모델 응답 + 검색 결과 + 그때 설정
    2) 에이전트/도구 실행 — 입력 폼 값 + 결과 + 실행 시간
    3) 이벤트 — 로그인/로그아웃, 업로드, 삭제, 에러

  ★ 처음 사람들이 잘 하는 실수:
    - 로컬 텍스트 파일에만 남기기 → 컨테이너 재시작 시 증발
    - 한 파일에 다 몰아넣기 → 며칠 후 분석 불가능
    - try/except 로 로깅 실패를 묻기 → "로그가 비었는데 왜죠" 미궁

  세 번째가 의외로 자주 발생합니다. 로깅 코드가 조용히 실패하지
  않게, 실패 횟수와 마지막 에러를 어디든 한 군데 (예: 캐시/관리자
  탭) 에 보이게 해두면 운영 중 큰 도움.


F. 사용자가 떠나지 않게 — UX 와 에러 안내
─────────────────────────────────────────

  서비스 사용자는 "Error code: 403" 한 줄 보면 5초 안에 떠납니다.
  특히 챗봇은 외부 API 의존이라 에러 표면이 넓어요. 다음 5가지는
  최소한 한국어로 안내해 두는 게 좋습니다.

    - 401/403 권한 없음          (토큰 잘못 / 만료)
    - 429 쿼터 초과              (잠시 후 재시도 안내)
    - 404 모델 없음 / 미지원     (다른 모델 선택 유도)
    - 네트워크 / 타임아웃         (재시도)
    - Gated 모델 라이선스 미수락 (해당 모델 페이지 링크)

  포맷은 ① 한 줄로 무엇이 잘못됐는지 + ② 사용자가 할 수 있는 1-3
  단계 액션 + ③ 펼치면 원본 에러 (개발자 / 관리자 보고용).

  추가 UX 디테일:

    - 로딩 상태 표시 (spinner, progress, status). 침묵 1초 = 망함.
    - 첫 사용자 화면 (empty state). "뭘 해야 하지" 헤매면 떠남.
    - 모바일 반응형. Streamlit 기본은 OK 이지만 한 번 검수 필수.
    - 좌측 사이드바 접기/펴기 동작 확인 (의외로 잘 망가짐).


G. 보안 — 사고 1순위만 막자
─────────────────────────

  완벽한 보안은 불가능하지만 "사고가 자주 일어나는 패턴" 은 정해져
  있어서 그것만 막으면 80% 는 됩니다.

  체크리스트:

    □ .gitignore 에 .env, .streamlit/secrets.toml, logs/, .data/
    □ git add -A 보다 명시적 파일 추가 (실수로 .env push 방지)
    □ 정기적으로 grep 으로 "sk-", "hf_", "tvly-" 같은 키 패턴 검색
    □ HF / OpenAI 토큰은 least privilege (필요한 권한만)
    □ Supabase service_role 키는 절대 클라이언트 코드에 두지 않기
    □ 사용자 입력으로 파일 경로 만들 때 정규화 (path traversal)
    □ 토큰 회전: secrets 한 군데서만 주입 → 코드 수정 없이 갱신

  ★ "토큰 회전" 시나리오만 잘 만들어두면 인원 변경, 키 유출 의심
    같은 상황에 코드 변경 없이 secrets 만 갱신 + reboot 으로 끝납니다.


H. 그래서 어디서부터 시작하나 — 권장 순서
─────────────────────────────────────────

  처음 만드는 사람이 한 번에 다 챙기려 하면 진척이 안 나옵니다.
  다음 순서로 점진적으로 쌓는 걸 추천합니다.

    1) 단일 사용자 데모를 먼저 완성 (Streamlit + LLM API + 채팅).
    2) RAG 추가 (문서 업로드 + 검색 + 인용).
    3) Streamlit Cloud 에 배포해서 다른 사람이 써보게 한다.
    4) 사용자 격리 (디스크 경로에 user_id) 와 인증 (익명 또는 로그인).
    5) 영속 로깅 (외부 DB) — 이때 비로소 "서비스" 의 시작.
    6) 친절 에러 메시지, 빈 화면, 진단 UI 같은 운영 정비.
    7) 점점 더 많이 쓰이면: 다중 공급자 / 비용 추적 / 모니터링 / 알람.

  각 단계는 사용자가 막혔다고 알려준 후에 추가하는 게 보통 옳습니다.
  미리 다 만들면 실제로는 안 쓰는 기능까지 떠안게 돼서 운영이 무거워
  집니다. 챗봇 서비스는 점진적으로 자라는 게 정상입니다.


I. RAG 품질을 한 단계 올리는 3가지
──────────────────────────────────

  기본 RAG (검색 → 컨텍스트 → 답변) 가 동작하기 시작하면, 다음 세 가지
  개선이 가장 ROI 높은 다음 스텝입니다. 본 프로젝트에 모두 적용돼
  있어서 강의 중 실제 동작을 보여줄 수 있어요.

  1) 의미 단위 청킹
     → 문서를 잘게 자를 때 "문자 600자" 가 아니라 "단락 경계 + 문장
       경계" 를 따라 자르기. 그래야 한 청크가 의미 한 덩어리가 되어
       검색이 정확해집니다.
     → 한국어는 "다/요/죠/음/됨/함" 같은 종결 패턴이 문장 경계 신호
       로 잘 작동.
     → 효과: 같은 PDF 라도 청크가 "중간에 끊긴 문장" 이 되지 않아
       사용자가 답변의 인용을 읽을 때 자연스러움.

  2) Vector DB (pgvector / Qdrant / Weaviate / ...)
     → 임베딩을 메모리 numpy 가 아니라 진짜 DB 에 저장.
     → 컨테이너가 재시작되어도 인덱스가 살아있고, 문서 수가 늘어도
       RAM 한도에 안 걸림.
     → ANN 인덱스 (HNSW 등) 가 큰 데이터에서 빠른 k-NN 검색을 보장.
     → Supabase 를 이미 쓰고 있다면 pgvector 가 가장 마찰 적음 — 한 번의
       SQL 로 확장 + 테이블 + 인덱스 + RPC 셋업 끝.
     → 본 프로젝트는 "dual-write" 패턴 채택: 로컬 numpy 와 pgvector 둘
       다 유지, 검색 경로는 토글로 선택. dev 환경 / 미설정 환경 호환.

  3) Agentic loop (자동 follow-up 검색)
     → 초기 검색 1회로 끝내지 말고, LLM 이 "정보 부족" 이라고 판단하면
       추가 검색 쿼리를 직접 발행하게 만들기.
     → 구현 방식: OpenAI function calling 의 search_documents 도구를
       LLM 에 노출. LLM 이 도구 호출 → 우리 retrieve 함수 실행 →
       결과를 다시 LLM 에 전달 → 최대 N 라운드 반복.
     → 효과: 비교/대조/다단계 reasoning 질문 (예: "X 와 Y 차이 + 각각
       의 데이터셋 결과 + 한계") 에서 한 번에 다 못 찾은 정보를 단계
       적으로 보강.
     → 한계: function calling 미지원 모델은 자동 폴백. 응답 시간 약간 ↑.

  ★ 셋 다 적용해도 "이 시스템이 정말 나아졌는가" 는 *측정* 없이 알 수
    없습니다. 다음 후속 작업은 평가 프레임워크 (golden 질문 셋 +
    Recall@k / MRR / Faithfulness 자동 측정) 가 가장 큰 ROI.

14. 마무리
────────────────────────────────────────────────────────────────

이 프로젝트는 "데이터 사이언티스트가 만든 작은 RAG 도구"가 "다수 사용자
가 매일 쓸 수 있는 챗봇 서비스" 로 진화한 결과입니다.

핵심 학습 포인트:
  1. RAG는 검색 + 생성의 결합 — 검색 품질이 곧 답변 품질.
  2. 검색은 단일 기법(dense)으로 부족 — 하이브리드 + 재정렬 + 쿼리 확장.
  3. LLM 공급자별로 API 양식이 다름 — 호환성 레이어가 필요.
  4. 사용자 데이터는 영속화 + 분석 가능한 구조 (JSONL → DB) 로.
  5. UI/UX가 곧 채택률 — 사이드바, hero, 인용 popover 모두 디테일.
  6. 배포는 보안 + 자원 제약을 처음부터 고려 (.gitignore, RAM, secrets).

서비스 관점 추가 포인트:
  7. "데모 → 서비스" 의 분기는 다중 사용자 + 영속 + 관측 + 에러 UX 의 4축.
  8. Cloud 의 ephemeral 파일시스템은 첫날부터 외부 영속 저장소를 설계.
  9. Silent exception 은 운영의 적 — 카운터 + 마지막 에러 노출 패턴 필수.
 10. 외부 API 의존은 다중 공급자 + 친절 에러 + 호환성 레이어로 방어.
 11. 보안은 secrets 단일 지점 + RLS + 토큰 회전 시나리오까지 고려.
 12. 서비스는 한 번에 완성 안 됨 — 사용자가 막힐 때마다 한 가지씩 보강.

RAG 품질 향상 포인트:
 13. 청킹은 "길이" 가 아니라 "의미 단위" — 단락/문장 경계 우선.
 14. Vector DB 는 메모리 한계 + 컨테이너 재시작 둘 다 해결. dual-write 시작.
 15. Agentic loop = 검색을 한 번이 아닌 LLM 이 판단해 반복하는 패턴.
 16. 평가 (golden set + 자동 메트릭) 없으면 "어떤 개선이 진짜 도움" 모름.

추가 질문/개선 요청은 issue로:
